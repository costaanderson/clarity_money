1. Visão Geral

01 / 14

Clarity Money é uma aplicação SaaS full-stack de single-repo construída com TanStack Start (SSR + server functions). Não é um monorepo com workspaces — é um único projeto onde o mesmo código-base gera tanto o bundle de cliente (SPA React) quanto o servidor Node.js/Nitro que serve as APIs e realiza SSR.

Padrão central: Server Functions (createServerFn) são funções TypeScript que rodam exclusivamente no servidor mas são chamadas como funções comuns no cliente, com type-safety ponta a ponta e sem camada REST manual.

4. Arquitetura de Runtime

04 / 14

O TanStack Start compila dois bundles: cliente (SPA React com code splitting) e servidor (Node.js via Nitro). No Vercel, o servidor roda como Serverless Functions com Node.js 24.

Fluxo de Request

1. Browser faz request
2. Vercel Edge Network recebe
3. Nitro (Node 24) processa:
├─ Rota API? → HTTP handler direto
└─ Rota de página?
├─ Executa server fns no servidor
├─ Renderiza React em HTML (SSR)
└─ Hidrata no browser (SPA)

Dois clientes Supabase

ClienteChave usadaEscopo
context.supabaseJWT do usuárioServer fns autenticadas — respeita RLS
supabaseAdminSERVICE_ROLE_KEYAPI routes e cron — bypassa RLS

Build Pipeline

npm run build → vite build
├── client bundle → dist/client/ (React SPA + chunks lazy por rota)
└── server bundle → dist/server/ (Nitro → Vercel Serverless Functions)

Preset: nitro vercel | Runtime: nodejs24.x | Entry: src/server.ts (SSR wrapper)

7. Autenticação e Segurança

07 / 14

Fluxo de autenticação

1. Browser → Supabase Auth (email/senha ou magic link)
2. Supabase retorna JWT (access_token)
3. Browser envia: Authorization: Bearer <JWT> em cada server fn call
4. auth-middleware.ts (servidor):
├─ Extrai Bearer token do header da request
├─ Cria client Supabase autenticado com esse token
├─ Valida via supabase.auth.getUser()
└─ Injeta context.supabase + context.userId na server function
5. Todas as queries do Supabase executam como o usuário → RLS ativa automaticamente

Camadas de proteção

CamadaMecanismo
Navegação de páginaTanStack Router — beforeLoad redireciona para /auth se não autenticado
Server FunctionsMiddleware requireSupabaseAuth obrigatório em todas as funções privadas
Banco de dadosRLS — policy auth.uid() = user_id em todas as tabelas
API routes públicas (leads)Token hash SHA-256 no header X-Lead-Token + rate limit por IP
Cron endpointCRON_SECRET validado via header Authorization: Bearer
Operações adminsupabaseAdmin (service role) exclusivo em arquivos .server.ts — nunca exposto ao bundle de cliente

8. Server Functions — Padrão Central

08 / 14

Server Functions são o principal mecanismo de comunicação cliente↔servidor. Não há camada REST convencional para dados autenticados. O framework serializa a chamada, rota para o servidor, executa e retorna o resultado com type-safety completa.

// Definição — src/features/tasks/lib/tasks.functions.ts
export const listTasks = createServerFn({ method: "GET" })
  .middleware([requireSupabaseAuth])          // valida JWT, injeta context
  .inputValidator((input) => input ?? {})    // validação/sanitização de input
  .handler(async ({ data, context }) => {    // context.supabase + context.userId
    const { data: rows } = await context.supabase
      .from("tasks")
      .select("*, clients(id,name,type)")
      .eq("user_id", context.userId);
    return rows ?? [];
  });

// Consumo no cliente — chamada de função normal, sem fetch/axios/REST
const tasksQ = useQuery({
  queryKey: ["tasks", { filter, range }],
  queryFn: () => listTasks({ data: { status: filter, range } }),
});

Convenção dos arquivos por feature

ArquivoResponsabilidade
src/features/*/lib/*.functions.tsServer functions do domínio — exportadas e importadas diretamente pelas páginas
src/features/*/components/*.tsxComponentes React reutilizáveis do domínio
src/routes/_authenticated/*.lazy.tsxPágina: importa server fns, monta UI com useQuery/useMutation

9. API Routes Públicas

09 / 14

HTTP handlers convencionais usados onde server functions não se aplicam: webhooks, OAuth callbacks, endpoints externos e cron jobs. Seguem o padrão createFileRoute + server.handlers.

EndpointMétodoAuthPropósito
/api/public/leads POST Token SHA-256 (X-Lead-Token) + rate limit IP Ingestão de leads de landing pages externas. Valida token, registra cliente em clients + log em lead_intake_log.
/api/public/diagnostico POST Público Recebe resultado do diagnóstico financeiro público e persiste em client_diagnostics.
/api/google/callback GET OAuth2 state param (userId|service) Callback OAuth2 unificado para Google Calendar e Google Drive. O state param codifica userId|calendar ou userId|drive para discriminar o serviço. Persiste em google_calendar_tokens ou google_drive_tokens. Redireciona para /configuracoes?connected={service}.
/api/cron/donna-briefing GET CRON_SECRET Bearer Chamado pelo Vercel Cron às 10h UTC (7h BRT). Itera todos os usuários em profiles, pula quem já tem briefing do dia. Para cada usuário: busca config de IA (provider/key do próprio usuário ou fallback para env), lê arquivos do Drive (se configurado), inclui novos leads das últimas 24h, gera via callAI() e persiste em donna_briefings. Retorna {processed, skipped, errors}.

Dependência de IA: A abstração callAI() suporta Gemini, Claude e OpenAI. O modelo padrão do app é gemini-3.6-flash — foi depreciado 2 vezes (2.5 → 2.0 → 3.6). Monitorar changelogs de todos os providers. Se usuário não configurar chave própria, toda a geração cai no GOOGLE_AI_API_KEY do app.
Supabase: Banco, autenticação e storage 100% centralizados no Supabase. Sem fallback. SLA depende do plano contratado (Free/Pro). Avaliar Pro para ambientes de produção com SLA garantido.
Escalabilidade: A arquitetura serverless do Vercel + Supabase escala horizontalmente por natureza. Gargalos esperados em crescimento: (1) limite de conexões Supabase no plano Free, (2) custo de chamadas Gemini por usuário/dia no cron.
